# 语音手势接入基线（E7 语音 / E1 手势）

更新：2026-10-23｜范围：**文档与脚本整理**，本轮不接页面、不改
`src/web/serve.py`、前端 JS 与测试。

本文把「E7 语音控制」和「E1 手势+表情交互」现有的**资产、板上实测数字、脚本、接入设计与边界**
收在一处，供下一步实现和排期直接引用。沿用[工作区总览](README.md)的三档口径，并额外区分
**本机核对**（本次在开发机读文件/算哈希）与**未测**：

| 档位 | 含义 |
|---|---|
| 文件存在 | 文件在本机路径下确实存在，或公开 URL 可下；只说明“有这个东西” |
| 本机核对 | 2026-10-23 在开发机上对文件本体做的只读核对（字节数、SHA-256、`strings`） |
| 板卡实测 | 2026-10-16 在 Atlas 200I DK A2（`Ascend310B1`）上跑出的数字，条件与原始数据见[硬件实测](../05-板卡连接与硬件实测.md) |
| 尚未测 | 没有数字，或数字不能当验收指标（单会话、样本不足、真值不逐帧） |

模型来源、候选对比与优先级见[语音与手势模型调研](19-语音与手势模型调研.md)与
[手势模型调研明细](20-手势模型调研明细.md)；本文不重复推导。

## 0. 结论速览

| 能力 | 资产 | 可用性 | 识别率 | 接入状态 |
|---|---|---|---|---|
| E7 语音识别 | WeNet offline encoder `offline_encoder.om` + `vocab.txt`（官方 Atlas 200I DK A2 语音样例） | **板卡实测通过**：10 轮文本一致，NPU 推理中位 **121.0 ms** | **未测**：1 段指令录音（三条全中）+ 22 s 非指令录音（零命中），样本量不足以给识别率/误报率 | 只做了脚本级验证；未接 `/api/cmd`、未接页面 |

| 页面/接口接入 | `POST /api/cmd`（`source=voice`/`gesture`）+ `interaction` 事件 | 接口已存在（`src/web/serve.py`），语音/手势侧**尚未有任何调用方** | — | **本轮不接**，原因与下一步见 §4 |（2026-10-30 更新：识别结果 → 指令的规则与 `/api/interact/*` 已在仿真落地，见[语音手势接口](25-语音手势接口.md)；识别端到接口的调用链仍未接）

一句话：**模型侧已经不是瓶颈**（语音 121 ms、手势 9 ms，板卡上确认）；现在缺的是
「识别率验收数字」和「从识别进程到 `/api/cmd` 的受控通路」。在这两件完成前，E1/E7
**不能作为自动分拣的主通道**（§3.5）。

**语音指令实测（同一批，`model_smoke_test.py asr` 跑在板上，录音在开发机）**，原始数据
[2026-10-16-asr-command-test.json](../hardware-test-results/2026-10-16-asr-command-test.json)：

- **真识别**：操作员依次说“启动 / 跳舞 / 停止”，20 s 录音 +16 dB、截到模型上限 14.7 s（1468 帧），
  3 次运行文本一致；前三个词正是三条指令且顺序正确，尾段是操作员自己的对话（经确认，不是幻觉）。
- **误报**：另一段 22 s、全程无指令词的录音切三段各 +20 dB，三段识别文本中**没有任何指令词**；
  纯数字静音 14.7 s 空输入输出为空。
- 结论：**“通用中文 ASR + 关键词匹配”方向可行**，但样本量是 1 段指令 + 1 段非指令，
  **不足以给出识别率与误报率**。

已知限制（详见 [19 号文档 §5](19-语音与手势模型调研.md) 与
[05 号文档](../05-板卡连接与硬件实测.md)）：

- 模型是**静态输入**：1478 帧 = **14.78 s** 上限，超长必须在前处理里截断。
- 后处理是**贪心 CTC，只给文本、不给置信度**；“是否命中指令”只能靠文本/拼音匹配，没有分数可用。
- 开发机麦克风电平偏低，实测需 **+16～+20 dB** 才可用；真实系统要有 AGC。
- 按噪声底自动裁剪不可靠（噪声底 −44.2 dB、`floor+8 dB` 会把 3.25 s 误判为起点，实际人声在 18.5 s 后）。
- 板上 USB 音频模块**仍未实测**；本次与官方样例一致，走“开发机/网页收音 → 下发”的兜底形态。
- 词表对“启动/跳舞/停止”的覆盖**未单独验证**，只有上述一次真实录音的证据。

### 1.3 识别率：已经测到的与没有测到的

**训练域（课程自带 `Gesture/val/<class>/`，每类等距抽 60 张，板上跑）**，原始数据
[2026-10-16-gesture-accuracy.json](../hardware-test-results/2026-10-16-gesture-accuracy.json)：

| 真实类别 | idx0 | idx1 | idx2 | idx3 | 正确率 | 该类平均概率峰值 |
|---|---|---|---|---|---|---|
| fist | **58** | 1 | 0 | 1 | **96.7%** | idx0 = 0.949 |
| like | 1 | **58** | 1 | 0 | **96.7%** | idx1 = 0.939 |
| ok | 0 | 1 | **59** | 0 | **98.3%** | idx2 = 0.970 |
| palm | 0 | 0 | 0 | **60** | **100%** | idx3 = 0.992 |

总体 **97.9%**。这同时是**标签顺序与课程 Notebook 一致**的决定性证据（`0=fist 1=like 2=ok 3=palm`）。

**现场域（腕部相机前真实做手势，每个手势一个会话、约 100 帧）**：

| 实际 | 帧数 | 判 idx0 | idx1 | idx2 | idx3 | 命中率 |
|---|---|---|---|---|---|---|
| fist | 101 | 6 | 0 | 0 | **95** | **5.9%** |
| like | 101 | 7 | **94** | 0 | 0 | 93.1% |
| ok | 102 | 1 | 14 | **87** | 0 | 85.3% |
| palm | 102 | 0 | 0 | 0 | **102** | 100.0% |

合计 **71.2%**，只有 `fist` 塌掉。**这组数字不能当准确率**：每类只有一个会话、相邻帧高度相关，
真值是“操作员当时比的是哪个”，不是逐帧标注；它只说明方向与失败模式。

**背景是主因，不是手型**：固定中心裁剪把合计从 71.2% 拉到 **92.1%（80% 裁剪最优）**，
`fist` 从 5.9% 到 77.2%；但没有任何比例对所有手势都好（`like` ≤70% 崩、`ok` ≤50% 崩），
说明要做的是**手部 ROI 检测**，而不是写死裁剪比例。

**结论：识别率仍未测（验收口径）。** 需求是 ≥3 类、≥80%、≤1.2 s（[需求规格](10-需求规格.md)），
现有 71.2% / 97.9% / 92.1% 三个数字分别属于「单会话现场」「训练域验证集」「离线裁剪实验」，
**都不能直接写成达标**；需要多会话、逐帧标注重测。

## 3. 接入设计（只设计，不实现）

### 3.1 目标数据流

```text
[麦克风 / 腕部相机]
        │  （板上：每线程自建 InferSession；收音按兜底方案从开发机/网页来）
        ▼
[识别进程：ASR 贪心 CTC + 关键词匹配  /  HRNet 四分类 + 多帧确认 + 手部 ROI]
        │  归一化成“意图”：{source, command, detail, confidence}
        │  去抖 / 冷却 / 阈值 / 任务状态检查
        ▼
POST /api/cmd  {cmd, source:"voice"|"gesture", ...}   ← 唯一入口，不直接碰控制台
        ▼
src/web/serve.py  →  控制台 /api/*（操作权、使能、revision、限位、禁入区）
        │  受理的指令写 interaction {source, command, detail, confidence}；拒绝只回 error
        ▼
机械臂（实机还需页面“现场确认”）
```

要点：**识别端只调 `/api/cmd`**，不直接调控制台、不自己判限位/禁入区；所有运动仍由
`serve.py` 转给控制台，安全检查保持在一处（[接口文档](15-接口文档.md) §8.1）。语音、手势、
定时都从这一个口子下发（`src/web/serve.py` 的 `SOURCES` 白名单已含 `voice`/`gesture`）。

### 3.2 指令映射（草案，需硬件组确认）

`POST /api/cmd` 的 `cmd` 白名单与行为见[接口文档](15-接口文档.md) §8.2。当前可落地程度不同：

| 来源 | 识别结果 | 映射到 | 现状 | 说明 |
|---|---|---|---|---|
| voice | “停止” | `{"cmd":"stop","source":"voice"}` | **可用**（`stop` 分支写 `stopped` 并放开操作权） | 任何时刻都应允许；不做“急停”承诺 |
| voice | “启动” | `{"cmd":"start","source":"voice"}` | **部分可用**：仿真后端可启动；实机后端任务启停尚未支持（`Capabilities.task=False`），返回 501 | 识别端必须把 501 当拒绝显示，不能假装启动 |
| voice | “跳舞” | `{"cmd":"run_preset","preset":"dance","source":"voice"}` | **未实现**：`run_preset` 返回 501，待硬件组提供预设动作（H2-8） | 预设动作没写之前不假造 |
| gesture | `palm` / `like` / `ok` / `fist` | 待定（候选：`set_mode`、`stop`、`run_preset`） | **未定**，只有 `stop`/`set_mode` 现在就能安全落地 | 四类手势的语义**必须由需求方确认**，不要按直觉绑定运动 |
| 任意 | 未知/低置信度/未命中 | 不下发 | — | 只写调试日志（实现上可直接丢弃），**不写 `interaction`**；识别不等于命令 |

约束：语音/手势**不得**映射到 `set_joints` / `move_to` / `gripper` 这类直接运动指令的任意参数，
只能走已定义的固定语义；否则一次误识别就可能产生不可预期的运动。

### 3.3 `interaction` 事件

字段按[日志契约](18-日志契约.md) §3 的拟定条目（`src/tools/log_contract.py` 的 `EVENTS`）：

| 字段 | 类型 | 是否必有 | 含义 |
|---|---|---|---|
| `source` | str | 必有 | `voice` / `gesture`（与 `POST /api/cmd` 的 `source` 一致） |
| `command` | str | 必有 | 实际下发的 `cmd`（如 `stop`、`start`、`run_preset`），不是识别原文 |
| `confidence` | num | 可选 | **手势**可给分类概率；**语音没有**（贪心 CTC 只给文本），不要编造 |
| `detail` | str | 可选 | 原始识别文本 / 手势标签 / 预设名 / 拒绝原因等，供页面展示和排障 |

现状与差距（本轮只记录，不改代码）：

- `interaction` 在事件表里仍是 **planned**（`src/tools/log_contract.py` 的 `EVENTS`），但 PR #1 的
  `serve.py` 已在两处写它：启动任务成功后写 `{source, command:"start"}`；新增定时任务时写
  `{source:"web", command:"add_timer", detail:<repeat>}`。正式接入前应按 [AGENTS.md](../../AGENTS.md)
  的流程把事件表状态改为 stable，再重新生成 `docs/contracts/log_event.schema.json`。
- **被拒绝的指令不写半条事件**（[接口文档](15-接口文档.md) §8.2）：拒绝由 `serve.py` 返回中文
  `error`，识别端把它当失败展示；只有真正被执行/受理的指令才写 `interaction`。
- 语音没有置信度，页面不能对所有 `interaction` 都假定有 `confidence`。
- 本文按符号名（`SOURCES`、`_cmd`、任务启动分支）引用；若后续按
  [F1 接口与前端改进建议](22-F1接口与前端改进建议.md) 重构，符号名与行号可能变化，以源码为准。

### 3.4 安全闸门（四条都必须过）

1. **操作权**：只有 `serve.py` 持有控制台的 token 与 owner；语音/手势不得绕过它直接调控制台。
   其他客户端持有操作权时按控制台返回拒绝（`src/teleop/core.py` 的 `enable`）。
2. **使能（enabled）**：运动前必须 `enable`，控制台使能只有 2 s、由网关后台定时续期（当前约 1 s
   一次）；任何 `source` 都不能免掉这一步。
3. **任务运行中拒绝**：任务运行中（`status.task.state == "running"`，或控制台 `busy`）时，
   语音/手势只允许 `stop`；其余指令返回拒绝（F1 网关对运行中任务的手动运动返回 409
   `task_running`）并说明原因。这条防止“分拣中比个手势把预设动作插进去”。
4. **实机需现场确认**：实机 `enable` 在控制台侧要求 `onsite=True` **且画面新鲜**
   （`src/teleop/core.py` 的 `enable`）。对外服务必须把页面上的现场确认透传到 `onsite`
   （`/api/cmd {"cmd":"enable","onsite":true}` 或 `/api/arm/enable`），并且语音/手势进程
   **不能自己产生**这个确认：识别侧只发指令，不发 `onsite`。这条透传链路随 F1 网关重构补齐，
   接 E1/E7 之前要在实机上联调确认，不能只看仿真。

补充：`stop` 在任何闸门下都应放行；`stop` 的语义是“停止后续指令”，不是急停，页面文案不要写成急停
（[AGENTS.md](../../AGENTS.md) 的安全约定）。

### 3.5 边界：识别率未测前，不能作为自动分拣主通道

- **自动分拣主通道仍是“扫描 → 检测 → 抓取/投放”闭环**（v3 YOLOv8n 检测器 + 多视角定位），
  类别判定只看检测与贴纸证据，**不看语音/手势**。
- E1/E7 目前只能作为**指令通道（旁路）**：启动/停止/预设动作，且 `start` 在实机尚未实现。
- 在识别率验收前，语音/手势**不得**：
  - 触发“自动分拣开始”而无需人工确认（仿真可先用于演示）；
  - 参与类别判定、投放决策或安全联锁；
  - 成为无人值守流程的一环。
- 兜底通道保留：网页手动控制始终可用；识别进程异常时不得影响控制台与分拣主流程。
- 验收口径（[需求规格](10-需求规格.md)）：E1 ≥3 类、≥80%、指令响应 ≤1.2 s；E7 三条指令安静环境
  ≥80%、指令到动作 ≤2 s；两者都还没有验收数字。

### 3.6 防误触（设计约束）

- **语音**：文本/拼音关键词匹配 + 去抖 + 冷却；至少连续 N 次命中（或同一句内多词）才下发；
  没有置信度，所以用“重复确认 + 有效窗口 + 冷却”代替分数。
- **手势**：阈值 0.6 + **连续 N 帧一致**（课程 Notebook 每 60 帧判一次 ≈8 s，必须改成逐帧/每 2–3 帧，
  并做多帧确认）；静态输入 224×224，必须加手部 ROI，否则背景主导。
- **会话开始**：识别进程启动后先进入“未武装”状态，需一次显式动作（页面点击/固定手势）才允许下发，
  避免上电即误触发。
- 所有识别结果都先写“意图”，再经路由；路由拒绝时只显示原因，不写执行事件。
