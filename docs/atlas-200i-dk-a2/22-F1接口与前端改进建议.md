## 0. 结论先行

PR 的分层方向是对的（控制台仍是唯一执行侧、网关不重复实现限位/禁区、按日志契约读日志），实测也能把 5 个页签和仿真控制台跑起来。但有三类问题会直接影响验收和使用：

1. **角度回读闪烁**：页面在两个数据源之间跳（控制台 pose ↔ 回放日志 pose），不是控制台抖动。
2. **轮次口径不对**：现在把 YOLO/流水线 `pipeline_start` 当轮次计数，回放/历史会把轮次翻倍；用户要的是“一次 start = 一轮，YOLO 只作本轮明细”。
3. **首屏重复收事件**：页面计数/故障分布/未知物体卡片约 2 倍，直接破坏 PR 自己写的“页面条数 = 日志行数”。

这 3 条都是小改动可以修的；§2 的其余问题按 P1/P2 排期即可。

## 1. P0：三个必须修的实测问题

### 1.1 角度回读闪烁：页面混用了两个 pose 源

**现象（实测）**：同一个页面连续采样 12 次 `/api/status`，顶层 `joints_deg` 在两组值之间跳：

```
top [112, 38, 74, 13, 92, 30] | arm [99, 125, 5, 5, 154, 90]
top [99, 125, 5, 5, 154, 90]  | arm [99, 125, 5, 5, 154, 90]
...
```

`arm.joints_deg`（控制台回读）一直稳定；跳的是顶层 `joints_deg`。

**根因（两处叠加）**：
- `src/web/serve.py:553` `_events_after()` 每读日志就把日志事件的 `pose` 写进 `State.note_pose()`（`serve.py:357`），即回放日志里的旧姿态；
- `serve.py:449-452` `State.status()` 顶层 `joints_deg` 用的是 `self.joints`（日志 pose），而 `arm.joints_deg` 用的是控制台 pose；
- 前端 `src/web/js/live.js:134` 用 `store.status.joints_deg ?? store.lastPose`，于是选中了会跳的日志值。

**最小改法（服务端一处 + 前端一处）**：
```python
# serve.py State.status(): 有控制台时只认控制台 pose，日志 pose 仅作无控制台时的兜底
def status(self):
    arm = self.arm()
    return dict(..., joints_deg=(arm.get("joints_deg") if self.backend else self.joints),
                arm=arm, ...)

# serve.py _events_after(): 有控制台时不再用日志 pose 覆盖
def _events_after(self, after):
    events, total = L.read(...)
    if self.state.console is None:
        for e in events: self.state.note_pose(e.get("pose"), e.get("t"))
    return events, total
```
前端把 `live.js:134`、`control.js` 里所有 `store.status.joints_deg ?? store.lastPose` 改成优先 `store.status.arm.joints_deg`（无控制台时才用日志 pose）。

**验证**：接仿真控制台、不操作机械臂，每 0.3 s 采样页面六轴显示 20 次，值应完全不变；再手动 jog 一步，所有值同一次更新为新姿态。

### 1.2 轮次按 YOLO 执行计数：应改成“任务轮次”

**现象**：
- 回放样例循环 2 次后页面显示“已完成 16 轮”（样例实际 8 轮）；`#chipTotal=454` 而 `/api/log total=281`；
- 换用真实任务时，日志里历史/回放的 `pipeline_start` 也会被算进“本轮/已完成”。

**根因**：`js/store.js` 每遇到 `pipeline_start` 就 `_roundNo += 1`；`round` 来自整份日志顺序，不区分“本次任务”与历史/回放。YOLO 流水线的一轮不等于用户点一次“开始”的任务。

**建议口径（用户已确认）**：
> 一次 `start`（网页 / 定时 / 按钮）= 一个任务 = 一轮；YOLO/流水线事件只作为本轮明细。历史与回放不计入任务轮次。

**最小实现（不引入大重构）**：
1. `State` 里加一个 `task` 小对象（或单独 `TaskState` 类）：
```json
{"id":"task...", "running":true, "source":"web",
 "rounds_requested":1, "rounds_done":0, "current_round":0,
 "started_at":1792..., "finished_at":null, "exit_code":null, "error":null}
```
2. `start` 成功后记录 `started_at`；`task.current_round` = `t >= started_at` 的 `pipeline_start` 数，`rounds_done` = 同范围的 `pipeline_end` 数；回放事件打 `replay: true` 并排除。
3. 加两个接口（或先只加 `GET /api/task`）：
   - `GET /api/task` → `{task:{...}}`
   - `POST /api/task {"action":"start"|"stop","rounds":1}` → 任务启停
   - `GET /api/log/records?since=<started_at>` → 任务范围内记录（round 从 1 重新编号）
4. 前端只显示 `status.task`：运行中“第 x/y 轮”，结束“已完成 n 轮”，无任务时“未启动任务（日志历史 N 轮，只读）”。

**如果暂时不想动后端**：至少把前端 `store` 的“已完成轮”改成唯一 `run` 去重，并在没有任务时标注“日志历史”，不要显示成当前任务轮次。这样能消掉“16 轮”的假数字，但仍是日志口径；建议还是采用任务口径。

### 1.3 首屏重复收事件：“页面条数 = 日志行数”在页面上不成立

**现象**：`#chipTotal=454` vs `/api/log total=281`；轮次 16 vs 8；异常表每行重复、分布计数翻倍、未知物体 2 条事件渲染 4 张卡片。

**根因**：`src/web/js/app.js:64-70` 先用 `fetchLog(0,2000)` 全量 push，`:80` 又 `feed.start(0)`；`api.js:89` 对 `0` 走 `since=0`，SSE 从第 1 行重放；`store.push()` 没有按 `seq` 去重。

**最小改法（二选一）**：
- `feed.start()`（不传 0）——`LogFeed.start` 里 `since ?? first.total` 会从日志末尾开始；或
- 保留 `start(0)`，但 `store.push()` 加 `if (event.seq <= this.lastSeq) return;`，并按 seq 排序。

同时建议修 `api.js:74-81` 的延迟基线：`_t0` 取第一条被收到的事件，重放场景下拿到的是旧事件 → 延迟恒为 0（页头显示 `0.00 s`）。把基线设为“最近一条回填事件的 t + 当时墙钟”，SSE 只收新事件后计算才有意义。

## 3. 接口与组件设计建议（分阶段，不作为本轮改动）

用户要的方向：**模拟服务和真实机械臂是同一等级的实现**；前端按能力裁剪，不在页面里写 `if sim`；机械臂接口按工作区控制台 §4 补全。建议分三步，每步都可独立合入：

### 第 1 步：最小补丁（1–2 天，风险低）
- 修 §1 的 3 个 P0 + §2 的 P1 中风险最低的（滑块、archive、token cookie）。
- `GET /api/status` 增加一个 `backend` 描述 + `capabilities`（哪怕先只有 `kind`），前端只用来显示“仿真/实机”徽章。
- 不新增包、不动目录结构。

### 第 2 步：执行侧适配器（2–3 天）
- 把 `Console` 抽成两个同级实现（仿真/实机），共享 HTTP 客户端；仿真多出任务启停/世界/检测，实机多出 `onsite`，任务能力先 `False`。
- 运行状态统一：`status.backend`、`status.arm`、`status.task`；任务一次 start = 一轮，`records?since=`。
- 前端只读 `backend.capabilities` 决定卡片/按钮；sim 才显示“桌上物块”和仿真工作台外链。

### 第 3 步：控制台 §4 全量代理（3–5 天）
- `GET/POST /api/arm/<path>` 代理 `jog/cartesian/gripper/pose plan+execute/home plan+execute/profile/record/sample/verify/freeze/calibrate/measure/export`；网关注入 owner、自动补 revision，控制台中文错误原样返回。
- 控制面板按能力显示：操作权/任务/六轴 jog+pose/观察位/直角移动/夹爪/档位/录制；标定/测量可先只开放 API。
- 前端组件抽 `components.js`（卡片/徽章/关节条/横幅/空态），sim/real 只靠 capability 分支。

### 任务与状态 JSON 建议（供第 2/3 步对齐）
```json
"backend": {"kind":"sim|real|null","name":"...","address":"...","connected":true,
            "capabilities":{"camera":true,"task":true,"pose":true,"onsite":false,"sim_world":true}},
"task": {"supported":true,"id":"task...","state":"idle|running|finished|failed|stopped",
         "running":true,"source":"web","rounds_requested":1,"rounds_done":0,"current_round":1,
         "started_at":1792...,"finished_at":null,"exit_code":null,"error":null},
"arm": {...,"joints_deg":[...],"chain_cm":{...},"limits":{...}}
```
任务接口建议：
```
GET  /api/task                               -> {task}
POST /api/task {"action":"start","rounds":1} -> {ok,task}
POST /api/task {"action":"stop"}             -> {ok,task}
GET  /api/log/records?since=<epoch>          -> 任务范围内记录（round 从 1 起）
```

## 7. 可直接贴到 PR 的评论摘要

> 实测发现 3 个 P0：① 角度回读闪烁——顶层 `joints_deg` 用日志 pose、`arm.joints_deg` 用控制台 pose，页面混用两个源；建议后端有控制台时只认控制台 pose，前端统一读 `arm.joints_deg`。② 轮次按 `pipeline_start` 计数，回放/历史会翻倍；建议改成“一次 start = 一轮”的任务口径，YOLO 事件只作明细。③ 首屏 backfill + `feed.start(0)` 导致事件重复，`#chipTotal=454` vs `/api/log total=281`；建议 `feed.start()` 或 store 按 seq 去重。另有滑块不回读、中文归档名 404、延迟估计恒 0、定时错过任务补跑、`--token` 页面白屏、CORS 通配、操作权不释放、revision 重试死代码等问题，已按 P0/P1/P2 整理在文档里。
