## 0. 问题是什么

当前前端把「操作任务」「实时回传」「物块位置」按**数据种类**拆开，分散在「概览」和
「手动操作」两个页签：相机一块、回读一块、三维一块、事件流一块、记录表一块。看一轮分拣
要来回切页签，而且各面板一直等权显示，当前处在哪个阶段完全看不出来。

期望是按**任务阶段**组织：有扫描步骤的任务，扫完应当把物块渲染进三维场景，然后接续抓取，
每个阶段有自己的反馈重点。

## 1. 已查明的事实

### 1.1 扫描结果已经在事件流里，前端把几何丢了

`pipeline_start` 的契约含义是「一轮分拣开始；**列出扫描找到的全部物块**」。样例日志实际内容：

```json
{"event": "pipeline_start", "run": "data/sim/pipeline/20261011_144716",
 "cubes": [[0.0, 11.0], [-8.3, 16.5], [10.3, 16.2], [-5.9, 9.4]],
 "registration": {"views": 4, "map_origin_base_cm": [0.07, 6.76, -1.42],
                  "yaw_deg": 0.02, "spread_cm": [0.0, 0.0, 0.01]}}
```

而 `src/web/js/store.js:52-53` 只取了长度：

```js
} else if (name === "pipeline_start") {
  if (this.current) {
    this.current.run = e.run;
    this.current.cubes = e.cubes?.length ?? 0;   // 坐标全部丢弃
  }
}
```

逐块事件用**同一个 `cube:[x,y]` 作标识**，例如
`{"event":"pipeline_sorted","cube":[0.0,11.0],"bin":"40","category":"recyclable","seconds":4}`。
所以「扫描时在哪 → 判成什么类 → 去了哪个桶 → 用时多少 → 失败原因」这条链路**现在就能从
事件流还原**，不需要新接口。

`registration` 里的配准质量（`views` / `yaw_deg` / `spread_cm`）目前前端完全没展示。
扫描配准不准是抓不到的头号原因，应当在扫描阶段结束时显眼给出。

### 1.2 三维视图的物块走的是仿真专用通路，实机上画不出来

```
scene3d  ←  /api/blocks  ←  console.world()  ←  GET /api/sim/world
```

`/api/sim/*` 只存在于 `src/sim/sim_server.py`，`src/teleop/server.py` 没有这组路由
（grep 确认）。2026-10-30 接实机实测：`/api/status` 的 `arm.blocks` 为 `null`。
`src/web/serve.py:750` 的注释也承认「执行侧没有这一层时 blocks 为空数组」。

**结论：接实机时三维视图永远画不出任何物块。**

### 1.3 实机其实有定位数据，只是没接

实机控制台 `/api/status` 的 `localization.board.objects[]`，由
`src/teleop/localization.py:104-106` 生成，每个物体带：

```
label, map_cm, base_cm, yaw_deg, height_cm, bbox, method, precision
```

以及 `attach_stickers()` 附加的官方模型类别。批级误差指标也已存在：

| 指标 | 位置 | 说明 |
|---|---|---|
| `reprojection_px` | `localization.py:114`（板相机） | 第 60 行已在用它把 > 3 px 的拒掉 |
| `map_fit_rms_mm` | `localization.py:211`（手机） | 平面拟合残差 |
| `precision`（逐物体，自由文本） | `localization.py:106` / `:208` | 板相机：`rough; tentative intrinsics, assumed 3 cm block and map placement`；手机：`~0.3 cm when the coloured face is on top (2026-09-26 check)` |

标定产物在 `config/calibration/`：`camera_intrinsics.json`、`hand_eye.json` 及若干变体。

**`src/sim/world.py` 里没有任何误差概念**（grep `precision|error|noise` 无结果）——仿真是精确的。

### 1.4 `base_cm` 同名不同义

| 来源 | `base_cm` 实际是 | 依据 |
|---|---|---|
| `src/sim/world.py`（`base_cm=` 那处，2026-10-30 在 551 行；该文件正被垃圾桶建模的工作改动，行号会漂） | 方块**几何中心** | 取 `c = b["pose"][:3,3]`；同一循环里用 `c[2] - BLOCK/2` 求底面可反证 |
| `src/teleop/localization.py:104` | 方块**顶面**中心 | 取 `map_to_base([x, y, .03])`；`src/teleop/web/app.js:167` 用 `base_cm[2] - .03` 求地面可佐证 |

两者差一个半边长到一个边长（1.5–3 cm）。`src/web/serve.py:754` 把仿真的 `base_cm`
改名为 `centre_cm`（名字正确），但 `src/web/js/scene3d.js:93-95` 当成底面画，导致物块
整体画高 1.5 cm（已在 PR 第二轮评审 2.1 提出）。

## 2. 决策

### D1 统一世界接口，实机与仿真答同一个端点

**已定。** 不采用「从事件流重建」的替代方案。

与[22 号文档](22-F1接口与前端改进建议.md) §3 的方向一致：「模拟服务和真实机械臂是同一等级
的实现；前端按能力裁剪，不在页面里写 `if sim`」。

> **与 22 号文档 §3 的冲突（必须注意）**：22 号把「桌上物块」定为仿真专属能力
> （`capabilities.sim_world`，原文「sim 才显示"桌上物块"和仿真工作台外链」）。
> **本文推翻这一条**：实机有 §1.3 的定位数据，物块在两端都应可用，差异由 D2 的误差字段
> 表达，而不是由能力开关裁掉。`capabilities` 其余部分不受影响。
> 若已有工作按 22 号 §3 在实现 `sim_world` 开关，需按本条调整。

### D2 接口必须自带误差，仿真也要显式填

**已定。** 这是 D1 成立的前提。

原先反对统一的理由是：仿真的 `/api/sim/world` 是模拟器内部真值（上帝视角），实机只能是视觉
估计，统一端点等于在接口层面假装实机也有真值。**该反对意见因 D2 而不成立**——只要误差随
数据一起给出，前端按误差决定画法，就不存在假装。

要求：

- 仿真**必须**显式填 `error_cm: 0` / `error_basis: "exact"`。**不能留空**——留空在前端只能
  当「未知」处理，那样统一就白做了。
- 误差分两级：批级（来自重投影或平面拟合）与逐物体级（顶面检测与侧面检测精度不同）。
- 逐物体 `precision` 目前是自由文本英文串，驱动渲染需要的是**数值（厘米）**；文本可保留为
  `note`，但不能作为唯一的精度表达。

### D3 三维里的物块必须带来源与状态，不同来源不同画法

**已定。**

| 来源 | 是什么 | 画法 |
|---|---|---|
| 本轮扫描确定（`pipeline_start.cubes` + 逐块事件） | 执行侧据此行动的决策快照 | 实心、类别色 |
| 实时定位预览（`localization.board.objects`） | 单帧视觉估计 | 虚线、半透明、标注误差 |
| 已处理完 | — | 变暗，或移到桶位 |

「根据不同任务有不同反馈」由此**从数据语义里长出来**，不是额外设计的装饰：扫描阶段看虚线块
逐个变实心，抓取阶段看当前块高亮、完成后变暗。

### D4 阶段状态由事件序列推断，不进契约；但给 `scan_view` 补 `of`

**已定。**

阶段不加显式字段：`scan_view` 来了即扫描中，`pipeline_start` 即进入逐块，`pipeline_end` 结束。
序列本身蕴含阶段，加字段冗余且会产生与序列不一致的风险。

**例外**：`scan_view` 必填字段只有 `run, view, pose`，**没有总视角数**，所以扫描过程中只能显示
「已扫 N 个」，做不了 `N/M` 进度条；总数要等 `pipeline_start.registration.views`，那时扫描已结束。

决定**给 `scan_view` 补 `of`**，理由是与项目既有用法一致——teleop 自己的 session 日志里
segment 事件就是 `{"index": 1, "of": 4}`。

- 设为 **optional**，不是 required：已有样例日志与历史日志都没有这个字段，设必填会让旧日志
  全部校验失败。
- 前端拿不到 `of` 退回显示计数，拿到则显示进度。
- 按 [AGENTS.md](../../AGENTS.md) 流程：先改 `src/tools/log_contract.py` 的事件表，再跑
  `python3 src/tools/log_contract.py schema > docs/contracts/log_event.schema.json`。

### D5 口径统一：`centre_cm`，中心

**已定。** `base_cm` 这个名字两端都不再用，统一为 `centre_cm` 并明确是**几何中心**。
`src/teleop/localization.py` 的顶面坐标需换算。**此项必须先于 D1 落地**，否则两条通路画出来
高度差 1.5–3 cm 且很难定位是哪错了。

## 4. 任务阶段 → 反馈映射

事件均来自[日志契约](18-日志契约.md)，无新增（除 D4 的 `of`）。

| 阶段 | 事件 | 携带 | 画面重点 |
|---|---|---|---|
| 扫描 | `scan_view` ×N | `view`（+`of`）, `pose`, `markers` | 臂在走位；已扫视角进度；认出的地图码 |
| 扫描完成 | `pipeline_start` | **`cubes[]`**, `registration` | **物块出现在三维里**；给出配准质量 |
| 逐块处理 | `pipeline_sorted` / `missed` / `skip` / `approach_failed` / `put_failed` / `cleared` | `cube`, `category`, `bin`, `reason` | 当前块高亮；完成按类别着色并连线到目标桶；失败标红并显示原因 |
| 抓取细节 | `gripped`, `put` | `grip`, `tip_cm`, `target` | 夹爪开合；末端到位 |
| 异常 | `pipeline_stuck`, `bin_full`, `stall`, `unknown_object` | — | 打断主流程，就地标注在出问题的那一块上 |
| 结束 | `pipeline_end` | 五项计数 | 本轮汇总 |

## 5. 工作区布局

现五个页签并为三个 + 调试收纳：

| 新页签 | 吃掉 | 内容 |
|---|---|---|
| **作业** | 概览 + 手动操作 | 三维场景为主画面；任务控制与阶段指示在其正上方；腕部相机贴在旁边（扫描阶段放大、抓取阶段缩小）；事件流降为侧栏时间轴并高亮当前块；逐块记录表只在一轮结束后展开 |
| **历史与告警** | 告警 + 告警（异常物体） | 失败事件、未知物体、逐块记录 |
| **任务计划** | 不动 | — |
| 调试/扩展 | 维持现有 ⚙ 收纳 | — |

原则：**让当前阶段决定界面重点**，而不是所有面板一直等权显示。

页面归属与验收口径以[23 号文档](23-前端功能收敛与验收口径.md) §1 为准，本节只改组织方式，
不改功能编号与验收数字。

## 6. 实施顺序与归属

顺序（底层先行，布局最后）：

1. **D5 口径统一**（`centre_cm`）——其余各项的前提
2. **D1 + D2 统一世界接口**（含误差字段，仿真填 0）
3. **D4 `scan_view` 补 `of`**（契约流程）
4. **D3 scene3d 按来源与状态分画法**（含修物块画高 1.5 cm）
5. **§5 工作区布局重排**

归属：**本套改动不进 PR #1**。PR #1 已 +4070 行，按第二轮评审的「必须修」四条修完即可合入；
本文这套是新工作，另开分支与 PR。混在一起会让作者分不清哪些是「写错了」、哪些是「要改方向」。

落点主要在 `src/teleop/`、`src/sim/`、`src/web/`，不涉及
[官方源码导入审计](06-官方源码导入审计.md)里的上游快照。

> **与在跑工作的冲突风险**：2026-10-30 建档时，工作区里有一批未提交改动正在动
> `src/sim/world.py`、`src/sim/sim_server.py`、`src/teleop/server.py`、
> `src/tools/log_contract.py` 与 `docs/contracts/log_event.schema.json`（垃圾桶建模与仿真联调，
> 见[24 号文档](24-垃圾桶建模与仿真联调.md)）。本文第 1–3 步要改的正是同一批文件。
> **开工前先确认那批改动已落地或已合并**，否则会相互覆盖。建档时已核：`scan_view` 仍无 `of`，
> `teleop/server.py` 仍无世界端点，`world.py` 的 `base_cm` 仍是旧语义——即本文各项都**还没有**
> 被那批改动实现。
