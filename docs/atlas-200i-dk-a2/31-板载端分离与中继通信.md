## 1. 分层

```text
┌──────────────────────── 板载端（Atlas 200I DK A2）────────────────────────┐
│ 相机服务 :8080 (仅本机)    /dev/video0 唯一持有者                           │
│ 控制台   :8765 (仅本机)    唯一的安全边界：限位、禁入区、租约、分段回读     │
│ 推理进程 (一模型一进程)    物块检测 / 语音 / 手势，结果经 HTTP 交给控制台   │
│ 任务执行器                 app/src/flow 各步 + 旧 pipeline，持控制台操作权      │
│ 板载网关 :8090 ──────────  对外唯一入口：鉴权、多端、推送、任务、世界、日志 │
└───────────────┬───────────────────────────────────────────────────────────┘
                │ USB 网络共享（或 OTG 网卡 + 网线）
        ┌───────┴────────┐
        │ 跳板手机（只转发）│  安卓 App 跳板角色，见 §2.1；电脑中继为备选 §2.2
        └───────┬────────┘
                │ 手机热点 / Wi-Fi（现场）、ZeroTier（远程）
     ┌──────────┴───────────┐
  网页前端（作业/仿真/历史）   Android App（控制为主）
```

原则：

1. **执行与安全全部留在板上。** 网关、任务执行器、推理都搬到板上；中继和客户端掉线不影响板上正在做的安全判断（租约到期即停）。
2. **中继只做网络，不跑业务。** 换一台中继（Windows/Mac/别的机器）不改一行业务代码。
3. **仿真是同一等级的执行侧。** 开发机上 `sim_server.py` 答与控制台相同的 `/api/*`，网关 `--console` 指向它即得到「仿真板载端」；前端与 App 不写 `if sim`，按 `capabilities` 裁剪（[23](23-前端功能收敛与验收口径.md) §3.8，`sim_world` 按 [26](26-工作区重构与统一世界接口.md) D1 改为两端都有世界接口）。
4. **控制台不对外。** 继续只监听 127.0.0.1，网关是它唯一的远程客户端（[15](15-接口文档.md) §8 原建议不变，只是网关从开发机搬到板上）。

## 2. 网络：安卓手机做跳板（2026-11-17 定为主方案）

跳板机用一部安卓手机，装我们自己的 App 并切到「跳板」角色；其他手机和电脑前端都经它访问板载网关。原来的电脑中继（§2.2）留作备选。

### 2.1 手机跳板

```text
板卡 ──USB 网络共享（手机→板）或 OTG 网卡+网线──▶ 跳板手机（App 跳板角色，前台服务）
                                                   ├─ 手机热点 / 同一 Wi-Fi：现场的手机、电脑直连
                                                   └─ ZeroTier：远程的手机、电脑
```

| 环节 | 建议 | 说明 |
|---|---|---|
| 手机 ↔ 板卡 | **USB 网络共享**优先；不行再用 OTG 有线网卡接板卡 `eth1` | USB 共享要求板卡内核有 `rndis_host`/`cdc_ether`/`cdc_ncm` 驱动，**未核对**；Android 11 起共享网段随机，板卡地址要靠发现（下一行） |
| 发现板卡 | 板载网关在共享链路上发 UDP 广播（或 mDNS），跳板 App 收到即记下地址 | 不写死 IP |
| 对外暴露 | App 只转发**网关一个端口**（TCP，承载 HTTP + SSE + 相机流），不做通用路由 | 安卓不 root 不能开 IP 转发，本来也只能做应用层转发；只开一个口，攻击面最小 |
| 远程入网 | **App 内嵌 libzt**（ZeroTier 的用户态 SDK），不走系统 VPN | 不占安卓唯一的 VPN 位，跳板手机还能开别的 VPN；libzt 的安卓绑定现状**未核对**，不行就退回「官方 ZeroTier App + 我们的 App 监听 ZT 地址」 |
| 现场确认 | **只能在跳板手机上点**，窗口 N 分钟 | 跳板手机用线连着板卡，人必然在机械臂旁，正好承担 §5 的现场确认 |
| 保活 | 前台服务 + 常驻通知；显示板卡链路、在线客户端数、流量 | 安卓会在后台杀进程 |

附带的一个选择：USB 共享时手机会把网也给板卡。若允许板卡上网，板上可以直接装 `zerotier-one`（§2.2 的 A），App 就不用转发了；**倾向不让板卡上公网**，ZeroTier 只在跳板手机上，板卡只认识跳板这一跳。

需要先确认的风险：

- **供电**：手机插在板卡 USB 上会向板卡取电充电，板卡 USB 同时给相机供电，可能拉低电压。要么关掉手机充电，要么经带外接电源的 HUB，实测前不要直接长时间插。
- 手机发热与续航、ZT 经根服务器中转时的延迟、跳板手机锁屏后转发是否断，都要实测。

### 2.1a 2026-11-17 手机调试记录（不接板卡）

条件：跳板手机 vivo V2339A（Android 16 / SDK 36），经 USB 连 Mac 并开 adb 调试；手机装官方 ZeroTier One 1.16.0；Mac 装 ZeroTier 1.16.2，同时开着 Clash Verge（mihomo）的 TUN 模式。Mac 扮演板卡：仿真控制台 `dev/sim/sim_server.py` :8770，加 `integration/pr1-pr2` 分支的网关 `app/src/web/serve.py --console http://127.0.0.1:8770 --port 8090`（只监听 127.0.0.1，启动配置 `gw-dev`）。没有发送任何实机指令。

| 项 | 结果 | 证据 |
|---|---|---|
| 手机 USB 共享用的协议 | **RNDIS**（不是 NCM） | `dumpsys tethering`：`mUsbTetheringFunction: RNDIS`，`tetherableUsbRegexs: [rndis\d]` |
| 由此推出：板卡要的驱动 | `rndis_host`（+ `cdc_ether`），板上**还没查** | 同上 |
| Mac 能否模拟这一跳 | 不能：Apple Silicon 的 macOS 不带 RNDIS 驱动。调试时改用 `adb reverse tcp:8090 tcp:8090` 代替「手机→板卡」这一跳 | — |
| 手机 → Mac 网关（adb reverse） | 通，`/api/health` 返回 200，TCP 建连约 20 ms（5 次 19–23 ms） | 手机 `toybox nc` 请求 |
| 手机上的应用层转发（免写代码的原型） | 通：`toybox nc -L -p 8091 toybox nc 127.0.0.1 8090`，在手机自己的 ZT 地址 `:8091` 上拿到网关响应 | 测完已关闭 |
| Mac 经 ZeroTier → 手机 `:8091` | **超时**（8 s） | `curl` 去掉代理环境变量后仍超时 |
| 超时原因 | Mac 的 ZeroTier 节点 `OFFLINE`：4 个根服务器都 `-1 RELAY`，连不上；路由表里 mihomo 的 `utun` 接管了默认路由，ZeroTier 的 UDP 被它截走 | `zerotier-cli info`、`peers`、`netstat -rn` |
| 附带的坑 | 终端里设了 `HTTP_PROXY`/`ALL_PROXY` 指向 Clash，`curl` 访问 ZT 地址时会经代理，返回 502；测 ZT 时要 `--noproxy '*'` 或清掉这些变量 | — |

结论：USB 这一跳和手机上的转发都通了；ZeroTier 这一跳**还没测出延迟**。手机侧 ZeroTier 是否在线没有单独核对（手机 `tun0` 已拿到 ZT 地址）。

**同日续查（20:36）**：Clash 配置里原本已有 `PROCESS-NAME,zerotier-one,DIRECT` 和两个旧根服务器的 TUN 排除；补上新根 79.127.159.187、84.17.53.155 与控制器 35.208.205.102 的直连/排除（备份 `*.bak-claude-20261117-203428`），重新激活配置并重启 ZeroTier 服务后：

| 对端 | 端口 | 出口 | 结果 |
|---|---|---|---|
| 网络控制器 35.208.205.102 | 36486 | en0 直连 | 通，251 ms |
| 4 个根服务器（planet 文件解析） | 9993 | en0 直连（已绕开 Clash） | 全部不通 |

**11-18 核对前一天能用的原因**：jetson-car 项目 11-17 白天的会话记录里，同一台 Mac、同一部手机经 ZeroTier 正常工作：14:09–15:37 时 Mac 的 en0 是 192.168.255.228，`zerotier-cli info` 为 ONLINE，4 个根服务器全部 DIRECT（160–260 ms）。当晚 19:47 后 Mac 换到了 10.61.x 网络（网关 10.61.0.1），从此 OFFLINE。ZeroTier 版本、Clash 规则（规则文件 11-10 修改）都没变，**唯一的变量是网络**。同一网络上 `tailscale netcheck` 报告 `UDP: true`，说明并非 UDP 全封，而是针对 9993 端口（或 ZeroTier 流量）。

判断（推断，未抓包）：Mac 当前所在 Wi-Fi 封了 UDP 9993。又因控制器的 UDP 有回包，ZeroTier 认为自己仍能直连公网，不会自动切到 TCP 中转，于是一直 `OFFLINE`。**对方案的含义**：ZeroTier 依赖 UDP，遇到封端口的网络（校园网、公司网常见）会整条断；实际使用时远程端所在的网络不可控，需要准备 TCP 兜底（`forceTcpRelay`）或在这类网络上换别的通路。

### 2.1b 2026-11-18 改用 Tailscale，App 跳板实测（仍不接板卡）

**虚拟网改为 Tailscale**（2026-11-18 定）：Mac 所在网络封 ZeroTier 的 9993，而 Tailscale 在同一网络 `netcheck` 报 `UDP: true`，打不通时还会自动退到 HTTPS 443 中转。跳板 App 只在本机虚拟网地址上做应用层转发，不依赖具体是哪个 VPN：网络放行 9993 时换回 ZeroTier 也能用（放行规则同时认 Tailscale 段 100.64.0.0/10 与本机 tun 网段）。手机同一时刻只能开一个 VPN。

条件：同 §2.1a 的手机（Tailscale 安卓版，节点 `v2339a`）、Mac（Tailscale 节点 `anweats-macbook-air`）；Mac 扮演板卡：`sim_server.py` :8770 + main 上的网关 `app/src/web/serve.py --console http://127.0.0.1:8770 --port 8090 --flow-python …`（启动配置 `gw-dev`，只监听 127.0.0.1）；手机经 `adb reverse tcp:18090 tcp:8090` 模拟「USB 共享链路上的板卡网关」。全部是仿真，**没有接板卡、没有发实机指令**。

| 项 | 结果 |
|---|---|
| Mac ↔ 手机 Tailscale | 直连打洞成功（`tailscale ping` 87 ms，未走 DERP）；ICMP 10 包 0 丢，平均 96 ms（19–123 ms） |

### 2.1c 手机接上板卡之后（步骤，未实测）

1. **接线前**：手机在 Mac 上 `adb tcpip 5555`，确认 `adb connect <手机 Tailscale IP>:5555` 能连；之后 USB 线要插到板卡上。
2. **供电**：手机插板卡 USB 会向板卡取电（§2.1 风险），先关手机充电或经带电源的 HUB。
3. **手机插板卡的 USB Type-A 口**（不是 Type-C，见 §2.1d），**开 USB 网络共享**（RNDIS），在板上查：`dmesg | tail`、`ip -4 addr`，应出现 `usb0`（或 `enx…`）并经 DHCP 拿到地址；没有就查 `modinfo rndis_host cdc_ether`。**这是第一项要实测的**。
4. **板上起服务**：相机、控制台（`--hardware --execute`，文档 32 §1.2 已取消 onsite）、网关 `src/web/serve.py --lan --port 8090 --console http://127.0.0.1:8765`（`--lan` 强制口令，口令填进 App 连接页）、`python3 scripts/board_beacon.py`（都在板上 `/root/arm-app` 下，即仓库的 `app/`；`scripts/board_up.sh` 一次起齐）。
5. **手机打开跳板**：板卡地址留空，等广播；连接页应显示「板卡 … （广播）· 网关建连 … ms」。
6. **Mac 经跳板上板**：`ssh -p 2222 root@<手机 Tailscale IP>`；部署脚本 `app/scripts/deploy.sh` 用 `BOARD_HOST`，可在 `~/.ssh/config` 里给跳板起个别名（`HostName <手机 IP>`、`Port 2222`、`User root`）再 `BOARD_HOST=<别名>`。
7. **调试手机**：`adb connect <手机 Tailscale IP>:5555`。

### 2.1d 2026-11-18 第一次接板：手机插板卡 Type-C 口不通

条件：手机 vivo V2339A（Android 16）用 C–C 线插板卡的 USB Type-C 口；经 Tailscale 的无线 adb 观察手机，未登录板卡，未发任何指令。

| 项 | 结果 | 证据 |
|---|---|---|
| 谁是主机 | **手机是主机，并向板卡这个口供电**（`data_role=host`、`power_role=source`）；手机电池在放电 | `dumpsys usb` port_manager、`dumpsys battery` |
| 板卡 Type-C 口报的是什么 | USB 设备「HISILICON Ethernet Gadget」，vendor 0x12d1 / product 0x107e，内核 5.10；**只有一个 RNDIS 配置**（RNDIS 控制 + RNDIS 数据），没有 ECM/NCM | `dumpsys usb` host_manager |
| 手机能否用它 | 不能：手机上没有出现任何 `usb*`/`eth*` 网卡（以太网服务在等 `(usb|eth)\d+`），即手机内核没有 RNDIS 主机驱动 | `/sys/class/net`、`dumpsys ethernet` |

结论：**板卡 Type-C 是 USB 设备口（RNDIS 网卡），不适合接手机**。按 §2.1 原方案，手机应插板卡的 **USB 3.0 Type-A** 口（板卡当主机），在手机上开「USB 网络共享」（RNDIS，手机当网卡），需要板卡内核有 `rndis_host`（未核对）。届时板卡地址可从手机 `dumpsys tethering` 的客户端里看到，不必等广播。

### 2.2 备选：电脑做中继的两种接法

| | A. 板卡自己入网 | B. 中继做路由 |
|---|---|---|
| 做法 | 中继给板卡共享上网（Windows ICS 的默认网段正是 192.168.137.0/24，与现有板卡地址一致）；板上装 `zerotier-one`（官方有 arm64 包），板卡成为 ZeroTier 成员 | 只有中继入网；在 ZeroTier 网络里加托管路由 `192.168.137.0/24 via <中继的 ZT 地址>`，中继开 IP 转发 |
| 客户端访问 | 直连板卡的 ZT 地址 | 访问 192.168.137.100，经中继转发 |
| 中继要做的 | 共享上网（NAT） | IP 转发 + 防火墙放行；Windows 需开 `IPEnableRouter`，Mac 需 `net.inet.ip.forwarding=1` 与 pf 规则 |
| 好处 | 中继换机器最简单；板卡还能拿到 NTP 校时（现在板卡时钟快 8 小时） | 板卡完全不上公网 |
| 风险 | 板卡暴露在 ZT 网络上，网关必须强制鉴权；板上 `zerotier-one` 的安装与内核 TUN 支持**未验证** | 客户端要接受托管路由（Android ZeroTier App 需开启）；中继的防火墙/代理 TUN 容易抢路由（Mac 上已遇到过 `utun0` 接管流量，见 [05](../05-板卡连接与硬件实测.md) 第 92 行） |

两种接法对上层完全一样：客户端拿到「板载网关地址」即可。地址与口令写在本机不入库的 `app/config/network.local.json`（仓库只放 `network.example.json`），**ZeroTier 网络 ID 不写进文档与代码**。

需要先实测、写进[硬件实测](../05-板卡连接与硬件实测.md)的数字：ZT 直连/经根服务器中转时的往返延迟与抖动、心跳 600 ms 下是否有租约误失效、MJPEG 640×480 经 ZT 的带宽与帧率。

两条已知约束：

- **Android 同一时刻只能有一个 VPN。** 手机开 ZeroTier 就不能同时开别的 VPN/代理。
- **画面要降档。** 远程默认给低帧率/低质量的 MJPEG（网关加 `fps`、`q` 参数），现场局域网再给全帧。

## 4. 对外接口（板载网关 v2）

**继承**现有网关的 `/api/cmd`、`/api/log*`、`/api/status(/stream)`、`/api/timers`、`/api/archive*`、`/api/interact*`，路径与字段不改。新增与调整：

| 接口 | 作用 | 说明 |
|---|---|---|
| `GET /api/info` | 版本、`backend`（`hardware`/`simulation`）、`capabilities`、网络入口（ZT/局域网） | App 首次连接与前端徽章用 |
| `POST /api/session/pair` → token | 客户端配对 | 现场显示一次性配对码，换长期 token；替代 `?token=` 拼在 URL 里 |
| `GET /api/world` | 统一世界（[26](26-工作区重构与统一世界接口.md) §3 草案） | 实机与仿真同一端点，带 `error_cm`/`error_basis` |
| `GET /api/flow`、`POST /api/flow/<step>` | 分步流程：`scan/locate/map/plan/execute/verify` | 每步一个会话目录（`app/src/flow/session.py`）；`plan` 返回路径供前端三维预览；`execute` 需操作权 |
| `GET /api/flow/<session>/<file>` | 取 `plan.json`、`collision_map.json`、`located.json` | 只读，目录边界校验沿用 `serve.safe_under` |
| `GET /api/camera/stream?fps=&q=` | 转发板载相机 | 远程默认降档 |
| `/api/control/*` | 操作权：`acquire`/`heartbeat`/`release`/`stop` | 包住控制台租约；**同一时刻一个写端**，其它端只读；`stop` 任何已配对端都可发 |

**日志契约**新增流程阶段事件（按 AGENTS.md 先改 `log_contract.py` 再生成 schema）：`flow_stage`（`session, step, state: started|done|failed, of, summary`）。`flow.jsonl` 仍留在会话目录，契约只收前端要显示的阶段摘要，不搬全部细节。

推送沿用 SSE（`/api/log/stream`、`/api/status/stream`）。App 端 OkHttp 有 SSE 支持；暂不引入 WebSocket，除非实测 ZT 下 SSE 断连频繁。

## 5. 远程控制的安全边界（必须先定）

> **2026-11-18：本节的「现场确认窗口」已由 [32](32-操作逻辑简化与分步任务.md) §1.2 / §6 作废**（不存在真正的远程端，取消 onsite，直接允许运动）；页面划分以 32 §4 为准。下表留作记录。

现有规则：实机 `enable` 要 `onsite: true`，PR #1 网关要求启动时加 `--onsite`。走 ZeroTier 后，**发指令的人可能不在机械臂旁**，这条必须重新表达：

| 建议规则 | 理由 |
|---|---|
| 实机运动只在「现场确认窗口」内允许：现场的人在板旁的局域网页面（或配对后在 App 上，且 App 与板卡同在 eth1/现场 Wi-Fi）点确认，窗口 N 分钟，过期回到只读 | 远程不在场时不能确认周围安全（AGENTS.md：执行前人工确认设备周围安全） |
| 窗口外：远程只能看状态、看画面、跑仿真、跑不动机械臂的 `locate/map/plan` | — |
| 断链即停：保持 2 s 租约不放宽；App 退到后台、断网、切页面都主动 `release` | ZT 抖动可能导致误停，宁可误停 |
| 点动只发离散小步，不做连续速度；App「按住连续点动」= 按住期间重复发单步，松手不再发 | 现有控制台本来只收小步，网络延迟只影响节奏，不影响单步安全 |
| 「停止」文案仍写「停止」，**不写急停**；`Arm_Action_Mode(0)` 未验证 | AGENTS.md |

## 7. Android App：跳板 + 控制

同一个 App 两种角色，启动时选：

- **跳板**（接着板卡的那部）：§2.1 的转发、发现、libzt、现场确认、保活；也可以同时当控制端用。
- **客户端**（其他手机）：经跳板的热点/Wi-Fi 或 ZeroTier 连网关，做下表的控制与查看；不能发现场确认。

现有 WebView 外壳保留给「作业/历史」浏览；控制部分改为**原生页面**，因为租约心跳、前后台切换、断网要和 App 生命周期绑定，WebView 里做不可靠。

| 页 | 内容 |
|---|---|
| 连接 | 扫码或输入网关地址 + 配对码；显示实机/仿真、ZT 延迟 |
| 控制 | 大号「停止」常驻；操作权状态与现场确认窗口倒计时；六轴点动（按住重复单步）、直角 XYZ/俯仰、夹爪三档、观察位/归位（先预览再执行） |
| 任务 | 一键分拣启停、分步流程逐步执行（每步展示产物摘要后再确认下一步）、当前块与阶段 |
| 画面 | 降档相机流小窗，可全屏 |
| 语音/手势 | 显示 `interaction` 事件与来源；识别本身仍在板上 |

包名 `com.example.myapplication00001` 需改为正式包名；`SimTaskClient` 换成接网关 v2 的客户端。
