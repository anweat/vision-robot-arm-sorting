## 0. 为什么要改（已查明，2026-11-18）

现在动一下机械臂要过的门：

| 门 | 现状 | 位置 |
|---|---|---|
| 使能 | 先点「使能」才拿到 2 s 租约；实机还要 `onsite: true` + 新鲜画面；过期就要重新使能 | `app/src/teleop/core.py` `enable()`、网关 `enableBtn` |
| 五个限位档 | `normal` / `explore` / `boundary`(60 s) / `grasp`(60 s) / `recover`(60 s)；各档允许的步长、能否归位、能否用姿态模式都不同，限时档到期自动退回并断租约 | `app/src/teleop/motion_policy.py` `profile_config()`、`core.py` 中 8 处按档判断 |
| 步长白名单 | 关节只收 ±1/2/5/10°，直角只收 0.5/1/2/3 cm、俯仰 1/2/5° | `core.py` `jog()`、`cartesian()` |
| 预览再执行 | 归位、姿态模式要先 plan 拿 `id`，30 s 内带同一 `revision` 再 execute | `core.py` `plan_home()`/`home()`、`plan_pose()`/`move_to_pose()` |
| `revision` | 每条指令都要带最新 `revision`，状态一变就拒绝 | `core.py` `_move()` |
| 速度 | 没有速度概念：`segment_ms`/`settle_ms`/`max_step_deg` 固定在配置里，`explore` 用快的一组（15°/400+120 ms），其余用慢的（5°/800+300 ms） | `app/config/arm_limits.json` `motion`、`motion_explore` |

这些门各自有来历（9–10 月实机调试中逐条加上），但叠在一起后，前端要处理「使能→选档→预览→执行→档位到期→重新使能」，手机上的摇杆根本没法接（摇杆是连续输入，不是一次一步）。

**保留不动的安全机制**（这些对操作者是无感的，不增加步骤）：

- 每段发送前整条路径的限位与禁入检查；不通过就一条都不发（`PlanRejected`）。
- 每段回读核对，偏差即「停在回读位」（`hold_at_readback`），不自动退回。
- 断链即停：租约（死人开关）保留，只是由客户端自动续，不再要人点。
- 实机画面过期即停。
- 「停止」任何端、任何来源（按钮/语音/手势）都可发，文案仍写「停止」不写急停（AGENTS.md）。

## 1. 控制台（板卡端运动接口）

### 1.1 一套限位，不分档

| 项 | 取值（建议） | 来自原来哪个档 |
|---|---|---|
| 关节限位 | `course_limits_deg`，J2–J4 下限放到 −10° | `explore` |
| 平台禁入 | **只提示**（2026-11-18 定）：`status` 照常给余量，不拒绝指令；靠阻力停保护 | `explore` |
| 桌面余量 | 0.5 cm（指尖离桌），**执行** | `grasp`（`explore` 只提示；任务本来就在 `grasp` 档的 0.5 cm 下跑） |
| 已在禁入区内 | 自动允许「余量不变差」的动作（原 `recover` 规则常开），不必切档 | `recover` |
| 边界测试 | 删除；需要摸边界时改配置文件，不在界面上给入口 | `boundary` |
| 逆解跳变上限 | 30° | `explore` |

`motion_policy.profile_config()` 收成一个 `runtime_config(base)`；`status` 里的 `profile`、`profile_remaining_s` 字段删除（前端同步删档位 UI）。`soft_limits_deg` 与 `keep_out` 照常在 `status` 里给出，供界面画范围。

两项开关写在 `app/config/arm_limits.json` 的 `runtime` 里（`enforce_platform`、`table_margin_m`），改配置不改代码。

### 1.2 去掉使能：隐式操作权 + 自动续租

| 原来 | 改为 |
|---|---|
| 点「使能」→ 拿租约 | **第一条运动指令自动取得操作权**（没人持有或持有者租约已过期时） |
| 人维持心跳 | 客户端在「页面可见 / App 前台 / 摇杆按住」期间自动发心跳（600 ms）；退后台、断网、关页自动停 |
| 另一端持有时报错 | 返回 409 `held_by`，界面给「接管」按钮（接管 = 先 `stop` 再取得） |
| 实机每次使能带 `onsite` | **删除**（2026-11-18 定）：不存在真正的远程端，调试时人就在旁边；`--hardware --execute` 启动的控制台直接允许运动。实机「画面过期即停」保留（自动，不增加步骤） |
| `revision` 每条都带 | 删除。它防的是「看着旧状态点了按钮」，但每段发送前都按当时的回读重新检查，旧状态不会变成越界指令 |

`stop` 依然清空操作权。

兼容：旧客户端发的 `/api/enable` 等同于「取得操作权」，`onsite`、`revision` 字段收到也忽略；`/api/profile` 返回「限位档已取消」。31 §5 的现场确认窗口作废。

### 1.3 速度：一个连续可调的量

速度只有一个参数 `speed`，单位 **°/s（单关节最大角速度）**，任何时候可改（运动中改，下一段生效），按客户端会话保存，控制台启动时取默认值。

| 量 | 由 `speed` 推出 |
|---|---|
| `segment_ms` | `max(250, 1000 × step_deg / speed)` |
| `max_step_deg` | `clamp(speed × 0.4 s, 3°, 15°)`：慢时分段细、快时分段粗 |
| `settle_ms` | `clamp(300 − 5 × speed, 120, 300)` |
| `readback_tolerance_deg` | 不随速度变；快时若频繁误判阻力，先加 `settle_ms`（与 `motion_explore._note` 的结论一致） |

| 档点（仅用于界面刻度，不是档位） | °/s | 对应原配置 |
|---|---|---|
| 最慢 | 3 | — |
| 原 normal | 6 | 5° / 800 + 300 ms |
| 默认 | 20 | — |
| 原 explore | 37 | 15° / 400 + 120 ms |
| 上限 | 40 | 未实测；上限写在 `arm_limits.json` `motion.speed_max_deg_s` |

接口：`POST /api/speed {speed}`；`status.speed`。任务执行器（第 2 节各步）用控制台当前速度，也可在任务参数里单独给 `speed`，但不超过上限。

### 1.4 运动指令收成四类

| 接口 | 用途 | 说明 |
|---|---|---|
| `POST /api/jog {joint, delta}` | 单关节相对点动 | `delta` 任意整数，\|delta\| ≤ 30°；按 `max_step_deg` 分段 |
| `POST /api/cartesian {axis, amount}` | 指尖沿 x/y/z（cm）或俯仰（°） | \|amount\| ≤ 5 cm / 15° |
| `POST /api/goto {pose \| named}` | 到绝对姿态或命名位（观察位、归位） | 全程检查通过才发；**不再分 plan/execute**。前端想先看路径，用 `?dry=1` 只返回分段与余量 |
| `POST /api/drive {mode, v[]}` | 摇杆连续驱动（新增） | 见 1.5 |
| `POST /api/gripper {action}` | `wide` / `open` / `grip` | 不变 |
| `POST /api/stop` | 停止 | 不变 |

### 1.5 摇杆连续驱动 `/api/drive`

控制台本来只收一次一步的指令；摇杆是连续量。做法是控制台里一个**驱动循环**，客户端只是不断刷新「我想要的速度向量」：

```text
客户端（10 Hz）  POST /api/drive {mode:"cartesian", v:[vx,vy,vz,vpitch], wrist:0}   每个分量 −1..1
控制台驱动循环   每段：目标 = 当前 + v × speed × 段时长 → 逆解 → 全程检查 → write6 → 回读核对
                 最近一次 drive 超过 300 ms 没刷新 → 停在回读位（死人开关）
                 v 全 0 → 停在回读位
```

- `mode: "cartesian"`：左摇杆 = 指尖水平移动（前后 = 沿径向，左右 = 绕底座转 J1），右摇杆 = 上下（z）与俯仰；`wrist` 为 J5 旋转（屏幕上的两个按钮）。
- `mode: "joint"`：左摇杆 J1/J2，右摇杆 J3/J4，`wrist` J5。供逆解够不到的位置用。
- 每段仍走 `_move` 的全部检查；被拒（越界、逆解跳变）时返回原因并保持原位，摇杆继续推也不会发出越界指令，界面在摇杆旁显示红色原因。
- 段时长取 150–250 ms（比 1.3 节的点动段更短，响应快）。**每段回读的耗时没有实测过**，实测前不能保证 10 Hz；先在仿真上跑通，再按 [硬件安全边界](../05-板卡连接与硬件实测.md) 以 3°/s 小步试。
- 实机只有六舵机批量写入可用（1–5 号单舵机写入不生效），驱动循环只用 `write6`，与现状一致。

## 2. 步骤独立：每一步都是一个可单独调用的「步」

### 2.1 步骤表

| # | 步 | 输入 → 输出 | 动臂 | 复用 |
|---|---|---|---|---|
| S1 | **扫描识别** `scan` | 扫描位姿 → 视图 + 识别结果 → `scene.json`（物块：位置、尺寸、偏航、**垃圾类别**、置信度、sigma；桶位） | 是 | `flow.scan` + `flow.locate` + `flow.build_map`（三步合一对外，内部仍分开、产物分别落盘） |
| S2 | **解算验证** `plan` | `scene.json` + 目标块 + 去处（桶/桌面点）→ `plan.json`（抓取候选、路径、每段余量、通过/拒绝原因） | 否 | `flow.plan` → `planning.plan_pick_and_place` |
| S3 | **抓取** `grasp` | `plan.json` 的抓取段 → 下探、合爪、抬起 → `grasp.json`（合爪读回） | 是 | `flow.execute`（只跑到 lift） |
| S4 | **抓后检查** `check` | 合爪读回 + 抬起后读回（滑脱判定）+ 腕部相机一帧（可选）→ `holding` / `empty` / `slipped` / `jammed` | 否（只读） | `console_grasp.grasp()` 里的读回判定与 `SLIP_DEG` |
| S5 | **空爪重试与报警** `retry` | S4 不是 `holding` 时：张爪抬起 → 就近重扫该块（S1 的局部版）→ 重解（S2）→ 再抓（S3、S4），最多 `retry.max` 次（默认 2）；仍失败或 `jammed` 时发**报警** | 是 | `console_grasp.wake_and_grip`、`GripMissed` 分支 |
| S6 | **放置** `place` | `plan.json` 的放置段 → 投桶/放桌面 → 松手 → 退回 | 是 | `flow.execute`（lift 之后） |
| S7 | **放置核对** `verify` | 放置前后两份 scene → 是否到位、其余块是否被碰 | 否（S1 扫描时动） | `flow.verify` |
| T1 | **语音唤起** `voice` | 识别文字 → 指令（启动/停止/单步名） | 否 | `app/src/interact/intents.py`、[25](25-语音手势接口.md) |
| T2 | **手势唤起** `gesture` | 手势标签连续 N 帧 → 指令 | 否 | 同上 |

你列的 6 项对应 S1–S5 + T1/T2。**放置（S6）和放置核对（S7）是补上的**：没有它们完整流程串不起来；S7 也是「这一块算不算分拣成功」的唯一依据。

### 2.2 每一步的统一约定（已实现：`app/src/flow/steps.py`）

每一步是 `fn(ctx, **参数) -> Outcome(result, summary, data)`，`result` 是一个短词，流程脚本按它分支：

| 步 | 动臂 | result（第一个为成功） |
|---|---|---|
| `scan` | 是（结束回观察位） | `done` / `empty` |
| `relocate` | 否 | `found` / `gone` |
| `plan` | 否 | `ok` / `rejected` / `no_destination` / `gone` |
| `grasp` | 是 | `done` / `failed` |
| `check` | 否 | `holding` / `empty` / `slipped` / `jammed` |
| `back_off` | 是 | `done` / `failed` |
| `place` | 是 | `done` / `failed` |
| `verify` | 否（核对前的 `scan` 动臂） | `ok` / `mismatch` |
| `home` | 是 | `done` / `failed` |
| `retry`（S5，单独执行时） | 是 | 跑 `app/config/flows/retry.yaml` |

单独执行一步：

```bash
python app/src/flow/orchestrator.py --step plan --session data/flow/S --block b2
```

```text
网关  POST /api/cmd {cmd:"flow_step", step, block?, session?}   不给 session 用最近一次流程的会话
```

- 会话目录 `data/flow/<时间戳>/`：每次扫描一个 `scan_NN/`（located.json、collision_map.json），每块一个 `blocks/<名>/`（plan.json、grasp.json、execution.jsonl）。单独执行的步从这里取上一步的产物，所以可以「扫描 → 看结果 → 解算 b2 → 看路径 → 抓 b2 → 检查」一步一步点。
- 不带 `--really` 时什么都不动：`scan` 要给 `source:`（一份 located.json），抓取/放置走空跑。
- 扫描后重新命名的块按位置找回（3 cm 内），找不到即 `gone`。
- `check` 只读 `grasp` 自己的记录：合爪读回（`holding` / `empty` / `not_closed`→`jammed`），抬起过程中 J6 再合拢 ≥3° 判 `slipped`（与 `console_grasp.SLIP_DEG` 一致）。

### 2.3 报警

S5 报警条件与处理：

| 条件 | 报警 `kind` | 机械臂停在哪 | 流程（`sort.yaml` 默认） |
|---|---|---|---|
| 重试 2 次仍空爪/滑脱 | `grip_failed` | 张爪、回观察位 | 记 `pipeline_missed`，跳过这一块；连续 3 块报警整轮停 |
| 夹在块上合不拢（`check` = `jammed`） | `jammed` | 张爪、回观察位 | 跳过这一块 |
| 抓取/放置中途停（偏差、阻力、起点不符） | `grasp_failed` / `place_failed` | 停在原地（执行器不自动恢复） | 整轮停 |
| 某步出了脚本没写分支的结果 | `<步>_<结果>` | — | 块内跳过这一块，块外整轮停；在 `retry.do` 里则只结束这次尝试 |

空中也合不上（舵机不响应）的判定在 `console_grasp.grasp()` 里，新流程还没接（`check` 只看读回，不做空中试合）。

报警的表现：日志 `alarm` 事件 → 网页顶栏红条 + 声音、手机系统通知（App 前台服务）+ 振动；板上若接了蜂鸣器/扬声器（语音模型所在的音频设备，未核对能否输出）可再响一声。报警要人在任一端点「知道了」才清除，不清除时完整流程不会自动开始下一轮。

## 3. 完整流程与触发模式

### 3.1 编排：YAML 流程脚本

完整流程写成 YAML 脚本（`app/config/flows/*.yaml`，2026-11-18 定），编排器 `app/src/flow/orchestrator.py` 只解释脚本、按顺序调第 2 节的步，**不另写抓取逻辑**。换顺序、改重试次数、开关逐块核对、加一步观察位，都只改 YAML。默认脚本是 [`app/config/flows/sort.yaml`](../../app/config/flows/sort.yaml)（带中文注释），结构：

```text
scan ──empty──▶ stop
for_each blocks (由近及远):
    plan ──rejected / no_destination──▶ record skipped，下一块
    grasp ──failed──▶ alarm grasp_failed，整轮停
    check ├─ holding ──────────────────────────────▶ （往下）
          ├─ jammed ──▶ back_off，alarm jammed，下一块
          └─ 其他 ──▶ retry ×2 until holding: back_off → scan → relocate → plan → grasp → check
                       └─ 用尽 ──▶ back_off，record missed，alarm grip_failed，下一块
    place ──failed──▶ alarm place_failed，整轮停
    record sorted
scan → verify (scope: round)
```

脚本语法（编排器只认这些，未知键在运行前就报错）：

| 键 | 含义 |
|---|---|
| `step: <名>` + `with: {…}` | 调一步，`with` 是该步的参数 |
| `on_result: {<结果>: [...], default: [...]}` | 按这一步的结果分支（不用 `on:`：PyYAML 会把 `on` 读成布尔 true） |
| `for_each: blocks` + `order:` + `do: […]` | 对扫描得到的块逐个执行；`order` 为 `reach`（由近及远）或 `scene`；不能嵌套 |
| `retry: {times, until, do: […], else: […]}` | 重做 `do` 至多 `times` 次，直到最后一步的结果等于 `until`；用尽执行 `else`。`do` 里没写分支的失败只结束这次尝试 |
| `alarm: <kind>` + `then: skip_block \| stop \| continue` | 发报警（`needs_ack: true`） |
| `record: sorted \| missed \| skipped` | 写 `pipeline_*` 逐块记录（只在 `for_each` 里） |
| `next_block: true` / `stop: <原因>` | 跳到下一块 / 整轮停 |
| 顶层 `speed: <°/s>` | 本流程开始时设给控制台 |
| 顶层 `stop_after_alarms: N` | 连续 N 块报警整轮停（默认 3） |

解析：有 PyYAML 用它；没有（板上未核对）时用 `app/src/flow/miniyaml.py`，只支持本目录脚本用到的子集，遇到锚点、标签、多行字符串直接报错；测试核对两者对 `sort.yaml`、`retry.yaml` 解析结果一致。

```bash
python app/src/flow/orchestrator.py --script app/config/flows/sort.yaml --check
python app/src/flow/orchestrator.py --script app/config/flows/sort.yaml --source data/flow/x/scan_01/located.json
python app/src/flow/orchestrator.py --script app/config/flows/sort.yaml --console http://127.0.0.1:8770 --really --log data/web/log.jsonl
```

- 「整轮一次核对」是为了省时间。要逐块核对，就在 `for_each.do` 末尾加 `scan` + `verify`（`with: {scope: block}`）。
- 中途随时「停止」：当前段走完后停在回读位，流程状态记为 `stopped`，不自动恢复；可从任一步单独继续。

### 3.2 触发模式

「模式」只决定**谁能启动完整流程**；停止永远所有来源都可以。

| 模式 | 启动方式 | 默认 |
|---|---|---|
| 按钮 | 网页/手机点「开始分拣」 | 开 |
| 语音 | 说「开始分拣」（`app/config/interaction.json` `voice.words.start`） | 关 |
| 手势 | `ok` 连续 3 帧（2026-11-18 定；`palm` 停止；`fist`/`like` 合爪/松爪不变） | 关 |

- 三种可同时开（多选）；`POST /api/mode {trigger:["button","voice"]}`，状态 `status.trigger`。**未实现**：现在仍是 `Interaction.armed` 一个开关管语音和手势两路。
- 语音/手势开着就是「武装」——原 `Interaction.armed` 开关并入这里，不再单独一个武装按钮。
- 语音/手势只能启动完整流程、停止，以及 2026-11-13 已确认的合爪/松爪，不能动臂（误识别的代价太高）；单步与点动只走按钮和摇杆。
- 网关的「开始」（按钮、定时、`start` 指令）已改为起编排器子进程跑 `sort.yaml`，事件写进网关活日志；「停止」同时终止该子进程。仿真控制台自己的 `/api/interact` 收到 `start` 仍走旧的 `run_pipeline.py`，未改。
- 有未确认报警时，经网关的语音/手势/定时启动被拒（页面按钮仍可）。仿真控制台自己的 `/api/interact` 不经网关，不受这条约束。
