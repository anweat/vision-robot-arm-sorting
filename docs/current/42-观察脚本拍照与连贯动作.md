## 1. 改了什么

| | 之前 | 现在 |
|---|---|---|
| 扫描位姿 | 写死在 `field_scan.SCAN_POSES` | 观察脚本 `app/config/observe/field.yaml`：位姿、顺序、每个视角等多久、要不要等控制台的定位结果、路被挡住时跳过还是停。`app/src/pipeline/observe.py` 执行，改完先离线核对 |

| 仿真测试 | 每个检查脚本各写一遍连接、布置、故障设置 | `dev/sim/harness.py` 共用；`dev/sim/bench.py` 按场景文件跑，`--set` / `--sweep` 改参数出对照表（[16](16-仿真模块.md) §7） |

## 2. 观察脚本

`app/config/observe/<名字>.yaml`（也可用 JSON）。整场扫描 `field.yaml`：

```yaml
name: field
title: 整场扫描
j5: roll_zero          # 夹爪滚转：roll_zero 或角度
settle_s: 0.8          # 两次回读相隔这么久、各关节相差 ≤ 1° 才算停稳
pause_s: 0             # 停稳后再多等这么久才拍
board: true            # 等控制台给出这个姿态的定位结果（地图码、官方模型检测）
on_blocked: skip       # 去某个视角的路被桶挡住：skip 跳过 / stop 整个停下
event: scan_view       # 每拍一张写一条的日志事件（日志契约 scan_view）
views:
  - {name: high_j1_100, pose: [100, 125, 0, 0]}
  - {name: near_j1_62, pose: [62, 106, 5, 0]}
  # ...
```

| 键 | 说明 |
|---|---|
| `views[].pose` | J1–J4，或 J1–J5（带 J5 时不看 `j5`） |
| `views[]` 上的 `settle_s` / `pause_s` / `board` / `j5` | 单个视角覆盖全局 |
| `views[]` 上的其他键 | 原样写进这一张的 `views.json` 条目，如桶视角的 `bin: 2` |
| `end` | 拍完去哪：`null` 不动、`observe` 回观察位、或 `[J1..J4]` |

每次移动都走 `console_grasp.move_to`（路径检查、被桶挡住时从上方绕），再经控制台自己的检查；每张照片都走 `capture.py`。产物和以前一样：`views.json` + `view_00.jpg …`，每条多了 `name`、`script`，以及照片的 `frame: {stamp, seq}`。

**改完先离线核对**（不动臂）：逐个视角查控制台的运行限位、方台余量，以及从上一个视角过去的路径（直接走 / 从上方绕 / 被拒）。

```bash
uv run --with 'opencv-python<5' --with numpy python app/src/pipeline/observe.py check field
uv run --with 'opencv-python<5' --with numpy python app/src/pipeline/observe.py run field --out <目录> --really   # 动臂；实机要现场确认
```

2026-11-21 `check field`：8 个视角全部通过，直接走，方台余量 +0.3 到 +3.4 cm。两侧近视角是 +0.3 cm，和 2026-11-14 调整时记的一致。

**哪些已经用上了观察脚本**：

- 整场扫描：`field_scan.scan(run, script=...)`。流程里 `scan` 多了参数 `observe`（默认 `field`，见 [35](35-流程脚本与前端整理.md) §2）。
- 桶视角：`field_scan.scan_bins` 从 `bin_views_<设计>.json` 生成脚本，遇到被挡照旧停下。
- 近看补拍（`run.refine`）和叠层测高视角（`stack_scan`）的位姿是按场景算出来的，不是固定的。它们暂时只换用了 `capture.py` 拍照，没有改成脚本。

`field_scan.SCAN_POSES` 仍然保留，从 `field.yaml` 读出，给读它的模块用。

## 3. 拍照

`app/src/adapters/capture.py`。单独拍一张：`python3 app/src/adapters/capture.py out.jpg [--console URL] [--no-board]`，不动臂。

一张能用的照片按三步判：

1. **停稳**：两次回读相隔 `settle_s`，每个关节相差都不超过 1°，两次控制台都不忙。2026-11-21 起前一次也不能忙，以前只看后一次。
2. **取帧**：取 `/api/frame`。控制台带 `X-Frame-Time` 时，只要比第一次“停稳”回读更晚的帧，3 s 内等不到就报错。两个时间都是板上的时钟，不用本机时钟比。旧控制台没有这个头，就照旧取到什么用什么。
3. **定位结果**（`board: true`）：等控制台对这个姿态、在停稳之后算出的定位结果，8 s 内没有就不带。一个视角看不到足够的地图码也照样有用。

## 4. 连贯动作

### 4.1 控制台：`POST /api/trajectory`

请求：`{waypoints: [[J1..J6], …], stops: [序号], dry?}`。

- **路点**：`null` 沿用上一个路点的值，第一个沿用上次指令。所以夹住块时 J6 保持合爪指令，不会变成回读的 129°。
- **先查整条链**：每两个路点之间按控制台的段长（随速度，[32](32-操作逻辑简化与分步任务.md) §1.3）切段，每段都按限位和禁入区查过，有一段不行就一段都不发。`dry: true` 只返回预览：段数、停点、预计秒数、最小余量。
- **中间段**：发完不等稳（`pass_settle_ms`，默认 0），读回落后命令不超过 `pass_tolerance_deg`（8°）不算遇阻。
- **停点和最后一个路点**：照常等稳（`settle_ms`），读回按 `readback_tolerance_deg`（4°）核对。
- **遇阻**：和其他动作一样，停在读回位置，不自动退回。
- **返回**：status，加上 `trajectory.reached`，即每个路点结束时的读回。

路径本身没变：仍是同样几条关节空间直线，每段的检查也一样。省掉的是中间每一步的停顿，以及停顿带来的往返请求、读回和修正。

### 4.2 流程：`app/src/flow/moves.py`

`stages.execute(..., motion="continuous")` 把要执行的步分成几段连发：

- 移动和张爪（open / wide / 任意 J6 张角）可以连在一起。放下时的松爪本来是 J6 点动，在轨迹里直接给 J6 目标角。
- **合爪单独发**：控制台要按回读判定 holding / empty，抓后检查要用这个判定。
- **放置的 lower 结束一段**（回读修正开着时）：在下放位先等稳、修正，再松爪（[40](40-垂直方向解算与叠放入桶.md) §1）。
- **张爪处停**：手指张开到位才继续走。每段最后一步之后照旧按读回修正、核对，和 steps 模式一样。

一次抓放（11 步）因此分成：

- 抓取：[到悬停、张爪、下探] → [合爪]
- 放置：[抬起、搬运、下放] → 修正 → [松爪、退开、回观察位]

`execution.jsonl` 每步一行，多了 `run`（这段从第几步到第几步）和 `stop`（这一步停没停）。没停的步记的是控制台在那个路点的读回。

### 4.3 流程脚本里怎么写

- 顶层 `motion: continuous`：这份脚本所有的 `grasp`、`place` 都连发。
- 单步写 `grasp` / `place` 的 `with: {motion: steps|continuous}`。
- 默认 `steps`，随应用发布的 `sort.yaml` 没有改。

## 5. 仿真结果

2026-11-21 在 Mac 上用 `dev/sim/bench.py` 跑，每种组合只跑了一次。

**这些数只说明几何和接口自洽。** 仿真舵机是瞬时到位的（只模拟了停短），所以省下的时间里没有实机读回滞后这一项。

### 5.1 等待和实机一样长（`arm-sim-1x`，`--speed 1`）

条件：场景 `vertical`，`stop_short_deg` 1.5，种子 3，真值定位，速度 20°/s（每段 8°、400 ms，等稳 200 ms）。产物在 `data/sim/bench/vertical/speed1x/`。

| 情况 | 逐步：成功 / 离目标 / 落差 / 执行 / 停顿 | 连贯：成功 / 离目标 / 落差 / 执行 / 停顿 |
|---|---|---|
| 叠放 A→B | 1/1，2.1 mm，5.0 mm，22.9 s，10 次 | 1/1，2.2 mm，7.0 mm，21.4 s，6 次 |
| 三层 C→A | 1/1，1.5 mm，8.4 mm，42.4 s，11 次 | 1/1，0.9 mm，4.7 mm，33.3 s，6 次 |
| 取下放桌面 | 1/1，0.7 mm，7.8 mm，43.7 s，12 次 | 1/1，4.4 mm，12.4 mm，28.9 s，6 次 |
| 放进桶（set） | 1/1，10.1 mm，13.9 mm，43.6 s，11 次 | 1/1，6.9 mm，18.9 mm，32.9 s，6 次 |
| 投进桶（drop） | 1/1，2.3 mm，49.4 mm，43.3 s，9 次 | 1/1，2.4 mm，51.3 mm，39.2 s，5 次 |
| 合计 | 5/5，195.9 s | 5/5，155.6 s（**少 21 %**） |

- **省时间**：每次抓放的停顿从 9–12 次降到 5–6 次。少掉的是中间各步的等稳（每段 200 ms），以及每步一来一回的请求、读回和修正。投进桶那例省得最少：它没有下放修正，逐步模式本来就少停几次。
- **准确度**：两种方式的离目标、落差都在同一量级，单次运行看不出谁更准。
  - 放进桶离目标 7–10 mm：两种方式都一样，回读修正都因为会碰桶壁被拒（[40](40-垂直方向解算与叠放入桶.md) §3.1），和连贯无关。
  - 取下放桌面那例，连贯是 4.4 mm / 12.4 mm，逐步是 0.7 mm / 7.8 mm。这次的修正也是因为会碰下面那块被拒，修不回来；要多跑几个种子才知道是偶然还是连贯带来的。
- **实机会省得更多**：实机舵机停短要靠修正补，逐步模式每一步都可能多一次修正移动（[32](32-操作逻辑简化与分步任务.md) 里抬升时停短 1–2°）。但实机多出来的读回滞后会吃掉一部分（§6）。实机能省多少要实测。

### 5.2 4 倍速（`arm-sim`，`--speed 4`）

| 场景 | 逐步 | 连贯 |
|---|---|---|
| `vertical`（同上，种子 3） | 5/5，执行合计 57.4 s | 5/5，45.1 s |
| `scan_place`（扫描定位后搬到桌面空位，`stop_short_deg` 1.0，种子 7） | 2/2，离目标 2.1 / 3.7 mm | 2/2，1.9 / 4.0 mm |

`scan_place` 每种情况前都按 `field.yaml` 扫描一次，扫描、观察脚本、拍照一层和连贯执行在同一条链路里跑通了，两种方式都没有任何接触。

`vertical`（1 倍速）里，两种方式都没有碰到桶壁和方台。夹爪碰到块（`block_contacts`）的次数：逐步 0 / 2 / 0 / 0 / 2，连贯 2 / 1 / 0 / 0 / 1，都出在叠放和投进桶这几例，是放下时碰到下面那块或桶里的块。

`scan_place` 第一版的空位离另一块太近，规划判夹爪会碰到那块，拒绝了。规划拒得对，场景里换了一个空位。

## 6. 上实机前

- **先量读回滞后**：中间段不等稳时，实机舵机的读回会落后多少还不知道。仿真舵机是瞬时到位的。
  - 先在 [硬件安全边界](05-板卡连接与硬件实测.md) 里核对，人工确认周围安全，以低速（如 6°/s）跑一条只有两三个路点、离桌面高的轨迹，看 `readback` 事件里 `passing: true` 那些段的偏差。
  - 偏差接近 8° 时，先把 `pass_settle_ms` 调大，不要先放宽容差。放宽容差等于放宽遇阻判定。
- **张爪不等稳的风险**：松爪之后马上退开。仿真里块是瞬时放开的；实机手指张开要时间，所以松爪设成了停点。实机上还要看退开时会不会带动块。
- **`sort.yaml` 不改**：实机核对之前，连贯模式只用于仿真和手动试验。
- **拍照的时间头**：`/api/frame` 的 `X-Frame-Time` 在实机上取自相机服务的 `X-Frame-Time`（板上时钟）。上板后用 `capture.py` 拍一张，核对 `frame.stamp` 和 `status.observed_at` 的先后。
