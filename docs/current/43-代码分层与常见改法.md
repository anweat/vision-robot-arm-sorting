# 43 代码分层与常见改法

更新：2026-11-27。范围：抓放主线的代码从流程脚本到舵机分了哪几层，要改一样东西该动哪个文件、怎么验证、要同步哪份文档，调参数去哪里找。目录放哪、怎么部署、怎么提交，见 [38](38-中期后开发指南.md)；实机上要测、要调的条目做成了卡片，见 [44](44-实机测试与调参清单.md)。

## 1. 从流程脚本到舵机

```text
流程脚本  app/config/flows/*.yaml               做哪些事、什么顺序、结果怎么分支（35）
   │      app/src/flow/script.py                解析与逐路径校验（网页、App、板上共用）
   ▼
编排器    app/src/flow/orchestrator.py          按脚本逐步调用；动臂前拒绝用到“不可用”能力的脚本
   ▼
能力 = 步骤  app/src/flow/capabilities.py       能力表，唯一来源：参数、结果、会不会动臂、状态
          app/src/flow/steps.py                 scan / plan / grasp / check / place …，每步 fn(ctx, **参数) -> Outcome
          app/src/flow/actions.py               pose / joints / gripper / led / wait_gesture …（不需要“当前块”的动作）
   ▼
阶段      app/src/flow/stages.py                scan → locate → build_map → plan → execute → verify，各写自己的文件
   │        ├─ 扫描  app/src/pipeline/observe.py   观察脚本 app/config/observe/*.yaml（42 §2）
   │        │        app/src/adapters/capture.py  停稳 → 停稳后的帧 → 板上定位结果（42 §3）
   │        │        app/src/pipeline/run.py、scene.py   建场景：视角联合配准、三路交叉核对（39）
   │        ├─ 规划  app/src/planning/            碰撞地图、抓取、放置、路径、读回修正（30、40）
   │        └─ 执行  stages.execute + flow/moves.py   逐步，或连成轨迹（42 §4）
   ▼
控制台    app/src/teleop/server.py、core.py     /api/pose、/api/trajectory、/api/gripper、/api/frame …；分段、限位、禁入区、读回核对
   ▼
舵机      Arm_Lib（只在板上）              仿真：dev/sim/sim_server.py，同一套控制台接口
```

几条贯穿各层的约定：

- **每一层都能单独跑。** 步骤的结果都写在会话目录里（`scan_01/located.json`、`blocks/<块>/plan.json`、`execution.jsonl`），所以任何一步都能从命令行单独执行，接着上一步的文件做（`orchestrator.py --step plan --session S --block b3`）。
- **动臂的只有控制台。** 上面各层只发姿态，分段、限位、方台禁入区和读回核对都由控制台负责；仿真控制台和实机控制台是同一套接口。
- **规划不看实机。** 规划只用碰撞地图和 `app/config/` 里的模型与余量。实机和模型对不上的地方，只能通过调参数修正（§4），不在代码里写特例。

## 2. 要改什么，去哪改

| 要做的事 | 改哪些文件 | 规矩 | 怎么验证 | 同步哪份文档 |
|---|---|---|---|---|
| 加一项流程能力 | 先改 `flow/capabilities.py`，再在 `steps.py` 或 `actions.py` 写同名函数 | 板上还没有接口的标 `unavailable` 并写 `needs`；新结果写进 `results`，只有成功的写进 `success` | `app/tests/test_script.py`（能力表与实现一一对应） | 35 §2 |
| 加或改一份流程脚本 | `app/config/flows/<名字>.yaml`（内置）；网页上保存的在 `data/flows/` | `off`、`on`、`yes`、`no` 要加引号；有动作的分支会显示成 failed，只写 `[]` 表示这个结果是预期的 | 网页「流程脚本」校验，或 `python3 app/src/flow/orchestrator.py --script <文件> --check`；再接仿真跑一轮 | 35 §10.1 |
| 换扫描路线 / 视角 | `app/config/observe/<名字>.yaml`；流程里写 `scan` 加 `observe: <名字>` | 视角不够时宁可多一个，不要贴着方台；`on_blocked` 默认跳过 | `python3 app/src/pipeline/observe.py check <名字>`（不动臂）；`app/tests/test_observe.py` 会核对这个目录里的每一份 | 42 §2、35 §10.2 |
| 改“什么帧能用”的规则 | `app/src/adapters/capture.py` | 所有扫描共用这一处，不要在各扫描里各写一份 | `test_observe.py` 的 CaptureTest；上板后 `capture.py` 拍一张核对时间（44 R03） | 42 §3 |
| 改抓放怎么发（逐步 / 连贯） | 分组规则在 `flow/moves.py`；控制台轨迹在 `teleop/core.py` 的 `trajectory` | 合爪必须单独发；张爪处和放下前修正前要停；控制台先把整条检查完才发 | `app/tests/test_motion_runs.py`；`bench.py run vertical --sweep execute.motion=steps,continuous` | 42 §4、15 |
| 改场景定位（块的位置、朝向） | `pipeline/run.py`（`cross_check`）、`pipeline/scene.py`、`spatial/view_bundle.py` | 环境变量 `ARM_SCENE_POSES=pnp`、`ARM_SCENE_ROI=off` 可以退回旧做法，方便对照 | `test_view_bundle.py`；`dev/tools/pose_loo.py`、`roi_bench.py real`（实机扫描离线重算） | 39 |
| 改规划（余量、放置、叠放、入桶） | `app/src/planning/`；数字在 `motion_planning.json`、`planning_tuning.json` | 改数字优先改配置，不改代码常量；说“够不到 / 无解”之前，先用正运动学暴力采样加网格模型核对解算器 | `app/tests/test_motion_planning.py`、`test_vertical.py`；`bench.py run vertical` | 30、40 |
| 加一种放法（如新的 `to`） | `flow/capabilities.py`（`plan.to`）→ `steps.plan` → `stages.destination` → `planning/release.py` | 放下后要不要更新场景，看 `steps._scene_after_place`：现在桌面和叠放会更新，进桶的不更新 | `app/tests/test_presets.py` 一类的单测，再加一个仿真场景 | 35、40 |
| 加一个仿真场景 / 调参对比 | `dev/sim/scenarios/<名字>.yaml`；参数前缀见 [16](16-仿真模块.md) §7 | 判对错用仿真真值；场景不经过流程脚本，直接调 `stages` | `bench.py run <名字> --set …`、`--sweep …` | 16 §7 |
| 加日志事件 | 先改 `app/src/tools/log_contract.py` 的事件表，再重新生成 schema | 前端只认事件表里的字段 | `app/tests/test_log_contract.py` | 18 |
| 统计读回偏差（HT01） | `dev/tools/readback_stats.py <会话目录或execution.jsonl> --json <结果.json>` | 区分方向、passing、有符号与绝对误差；缺读回不补零 | `dev/tests/test_readback_stats.py`；整轮集成产物 | [46 §4](46-无需硬件的集成测试与统计.md#4-读回统计ht01d1) |
| 离线整轮/异常回归与验收统计 | `dev/tools/offline_acceptance.py`、`acceptance_stats.py` | 明确区分软件成功、独立落点证据、未完成/缺失记录 | 一条命令出测试报告和完整会话 | [46](46-无需硬件的集成测试与统计.md) |
| 网页 / App 新功能 | `app/src/web/`、`app/mobile/android/` | 控制台自带的遥控页只修妨碍调试的问题 | 接仿真手点一遍；App 跑 `testDebugUnitTest` | 35 §5 |

## 3. 验证的台阶

一项改动从下往上走，每一级通过再上一级。哪一级能证明什么不一样：前四级只能说明几何与接口自洽，**只有后两级是实机结论**。

| 级 | 做什么 | 命令 | 说明什么 |
|---|---|---|---|
| 1 | 单测 | §5 的两条 | 规则没写错、各层接口对得上 |
| 2 | 离线 | `observe.py check`、`orchestrator.py --script … --check`、`dev/tools/flow_on_scans.py`（拿 28 次实机扫描重新规划） | 不动臂：姿态合法、脚本合法、实机场景下能不能规划出来 |
| 3 | 仿真 4 倍速 | 启动配置 `arm-sim`（端口 8770）；`bench.py run …` 或 `orchestrator.py --console http://127.0.0.1:8770 --really` | 整条链路跑通，碰撞计数为 0 |
| 4 | 仿真 1 倍速 | 启动配置 `arm-sim-1x`（端口 8773），等待时间和实机一样 | 耗时比较（两种发送方式、扫描视角数） |
| 5 | 实机低速 | 速度 6°/s 左右，离桌面高、动作少；先按 [05](05-板卡连接与硬件实测.md) 核对，人工确认周围安全 | 读回滞后、碰撞余量是否和模型相符 |
| 6 | 实机正常速度 | 默认 20°/s，按 44 的卡片执行并记录 | 精度、成功率、耗时 |

## 4. 参数在哪

改参数的规矩：

- 一次只动一个。
- 改之前先记下原值。
- 改完先在仿真里重跑受影响的场景，再上实机。

实机上测出来的偏差写进 `planning_tuning.json` 的 `trims`（这一节就是为实机微调留的），不要改模型本身的数字。

| 参数 | 文件 | 现值 | 管什么 | 谁来定 |
|---|---|---|---|---|
| `motion.speed_default_deg_s` / `speed_max_deg_s` | `app/config/arm_limits.json` | 20 / 40 | 控制台速度；33°/s 曾被实机否决（夹空与阻力误报增多，35 §9.1） | 实机 |
| `motion.settle_ms`、`readback_tolerance_deg` | 同上 | 300 ms、4° | 每段的等稳时间、遇阻判定 | 实机；**不要为了“少报遇阻”放宽容差** |
| `motion.pass_settle_ms`、`pass_tolerance_deg` | 同上 | 0 ms、8° | 连贯模式中间段（42 §4）；偏差大时先加等待，再考虑容差 | 实机（44 R05） |
| `execute.settle_deg`、`extra_deg`、`tries` | `app/config/planning_tuning.json` | 1.5°、3°、2 次 | 每步之后按读回补发（舵机停在指令前） | 实机（44 R04） |
| `trims.table_z_m` | 同上 | 0 | 桌面高度修正（触地标定的结果写这里） | 实机（44 R01） |
| `trims.grasp_offset_m`、`place_offset_m` | 同上 | 0 | 抓取 / 放下位置的系统偏差，[沿半径向外, 左, 上]，米 | 实机（44 R07） |
| `trims.grip_command_deg` | 同上 | 133 | 合爪指令；实机 3 cm 块读回 127–129 | 实机（44 R06） |
| `trims.j5_trim_deg`、`pad_centre_height_m` | 同上 | 0、0.018 | 旋腕零位、合爪时指垫中心离块底的高度 | 实机 |
| `errors.*` | 同上 | 见文件 `_sources` | 各输入的最坏误差，决定所有余量的宽窄 | 实机统计后更新 |
| `release.stack_gap_m`、`max_block_tilt_deg.stack` | `app/config/motion_planning.json` | 6 mm、8° | 叠放时松爪高度、允许的倾斜 | 实机（44 R09） |
| `release.table_gap_m`、`bin_clearance_m`、`over_rim_extra_m`、`max_block_tilt_deg.bin_set` | 同上 | 3 mm、1.5 cm、[0, 1, 2] cm、25° | 桌面放下、进桶下放 | 实机（44 R08） |
| `release.min_extra_gap_m` | 同上 | 8 mm | 最窄的张爪比块宽多多少 | 实机（44 R06） |
| `MIN_ERROR_M`、`MAX_ERROR_M`、`TRIES` | `app/src/planning/correct.py` | 1.5 mm、12 mm、2 次 | 放下前按读回修正：多小不修、多大不信、修几次 | 仿真定的，实机核对（44 R07） |
| `settle_s`、各视角 `pose` | `app/config/observe/field.yaml` | 0.8 s、8 个视角 | 扫描每处等多久、从哪看 | 实机（44 R02） |
| `TABLE_AREA_M`、`SPOT_CLEAR_M`、`SPOT_MIN_MOVE_M`、`TOWER_LEVELS` | `app/src/flow/steps.py` | 见代码 | 搬运找空位的范围与间距、叠积木的层数 | 实机（44 R10、R09） |
| `ROI_AGREE_CM`、`ROI_AGREE_DEG` | `app/src/pipeline/run.py` | 0.4 cm、6° | 三路交叉核对时，几种估计算一致的门槛 | 实机扫描（44 R12） |
| `min_views` | 流程脚本 `scan` 的参数 | `gesture_sort` 里是 3 | 视角太少的检测当噪声去掉；依赖扫描覆盖（35 §9.3） | 实机扫描 |

表里“现值”是 2026-11-22 的。改了就在对应文档里写日期、原值、新值和依据。

## 6. 容易踩的坑

- **控制台地址是导入时拷的。** `field_scan.BASE`、`console_grasp.BASE` 是导入那一刻从 `console_step.BASE` 拷的副本；改了 `--console` 之后它们不会跟着变。新代码一律在调用时读 `console_step.BASE`，或者像 `capture.py` 那样传 `console=None`。
- **放下后场景不重扫。** 叠积木和搬运放下后，按规划的落点更新场景，接着处理下一块。所以这两份脚本里不要加 `scan`：普通扫描把每块都当成放在桌面上，会把塔“摊平”。
- **仿真偏乐观。** 仿真渲染和定位用的是同一个相机模型，检测框比实机准，舵机瞬时到位（除非开 `stop_short_deg`、`pose_jitter_deg`）。仿真的数字只能用来比较方案，不能写成实机能力。
- **`run/retry_*` 不入库。** 旧流水线夹空重试时，会把重扫的照片写进当前目录下的 `run/`，提交时不要带上。
- 板卡时钟、OpenCV 版本差异、Windows 软链接这几个坑见 [38](38-中期后开发指南.md) §5。
